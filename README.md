# my-site

Сайт-визитка с автоматическим CI/CD через GitHub Actions

## О проекте

Простой статический сайт (HTML, CSS, JavaScript) с автоматической проверкой качества кода и публикацией на GitHub Pages

- **Сайт:** https://apoll-plesh.github.io/my-site/
- **CI workflow:** [.github/workflows/ci.yml](.github/workflows/ci.yml)
- **CD workflow:** [.github/workflows/cd.yml](.github/workflows/cd.yml)

## CI/CD

**CI (`ci.yml`)** запускается на каждый push в `main` и на каждый Pull Request в `main`:
1. Устанавливает зависимости (`npm ci`)
2. Проверяет HTML-код линтером (`npm run lint`)
3. Запускает тесты (`npm test`)
4. Собирает прод-версию в `dist/` (`npm run build`)
5. Загружает `dist/` как артефакт

**CD (`cd.yml`)** запускается после успешного завершения CI на ветке `main`:
1. Скачивает артефакт `site-build` из CI
2. Публикует его на GitHub Pages

## Ответы на вопросы

### Чем отличается CI от CD?

**CI (Continuous Integration)** — автоматическая проверка каждого изменения: сборка, линтер, тесты. Цель — как можно раньше обнаружить проблемы в коде

**CD (Continuous Delivery / Deployment)** — автоматическая доставка проверенного кода в продакшен. Цель — быстро и надёжно публиковать изменения

Ключевое отличие: CI проверяет, CD публикует. CD возможен только после успешного CI

### Что произойдёт, если тесты завершатся ошибкой на этапе CI?

Job `ci` завершится со статусом failure. Поскольку деплой зависит от успешного CI (через `needs: ci` в исходной конфигурации или через `workflow_run.conclusion == 'success'` в разделённой), он не запустится. Сайт на GitHub Pages не будет обновлён — в прод не попадёт нерабочий код. Разработчик увидит красный крестик во вкладке Actions и сможет изучить лог ошибки

### Для чего используется директива `needs: ci` в задаче развёртывания?

Она задаёт зависимость: job деплоя не начнётся, пока CI не завершится успешно. Это защищает продакшен — если код не прошёл проверку (линтер, тесты), публикации не будет. Без `needs: ci` оба job'а запускались бы параллельно, и сломанный код мог бы попасть на сайт

(В разделённой конфигурации эта роль выполняется через `workflow_run` с условием `if: conclusion == 'success'`)

### Что такое артефакт и для чего он передаётся между задачами?

**Артефакт** — это файл или набор файлов, которые один job сохраняет, а другой job может скачать. У нас артефакт — это папка `dist/` с готовой сборкой сайта

Передаётся между job'ами потому, что job'ы выполняются на разных машинах (runner'ах) и не видят файлов друг друга. Job `ci` собирает проект и выкладывает артефакт через `upload-artifact`; job `deploy` скачивает его через `download-artifact` и публикует. Это гарантирует, что публикуется ровно та сборка, которая прошла проверку

### Почему развёртывание не запускается на Pull Request?

Потому что деплой ограничен условием — либо `if: github.ref == 'refs/heads/main'` (в исходном варианте), либо триггером `workflow_run` с `branches: [main]` (в разделённом). При PR ветка — не `main`, а `refs/pull/N/merge`, поэтому деплой пропускается

PR — это ещё не принятое изменение. Оно может быть отклонено, содержать ошибки или быть вредоносным. Публиковать его на прод-сайте нельзя. На PR запускается только CI — чтобы проверить, что изменения не ломают проект. Деплой произойдёт только после слияния в `main` и последующего push
